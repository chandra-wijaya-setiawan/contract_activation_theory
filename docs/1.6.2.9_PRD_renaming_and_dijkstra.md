## 1. Background

The framework is named **Contract Activation Theory (CAT)** but the code uses
generic ML-agent vocabulary (planner / executor / judge / decompose / invoke).
That mismatch creates a two-vocabularies problem: every doc edit risks
drifting from the code, every new contributor needs a mental translation
table, and the legal-contract analogy (which is the framework's distinctive
contribution) lives only half in code.

This PRD locks in **one vocabulary across code and docs** — the legal-contract
vocabulary — for the 4-6 names where the engineering term actively competes
with the legal one. It also formalizes where a future Dijkstra-style
candidate-evaluation layer would sit in the renamed loop.

## 3. Non-goals (explicitly NOT renamed)

Keep these because the engineering and legal terms agree, or because the
class name carries the framework's signature concept:

- `Contract`, `Constraint`, `Criterion`, `Representation` — already legal terms.
- `Activator` — daemon-analogy signature. Legal note: activation = formation/execution.
- `Representer` — class that does REPRESENT step; "representation" is legal.
- `_verify_criteria` (method name in activator) — "verify" is itself legal.
- `Recorder`, `RunDAG`, `RunMetrics` — engineering scaffolding, no role conflict.
- `ContractState` enum values (`LATENT / ELIGIBLE / ACTIVE / SUSPENDED / FULFILLED / FAILED / EXPIRED`) — already legal lifecycle terms.

## 5. Dijkstra layer mapping (design, not implementation)

The Dijkstra-style cost-aware search layer would sit inside Step 6 PERFORM
(formerly INVOKE), specifically by splitting it into three sub-steps:

```
Step 6 PERFORM (currently one LLM call) — would split as:

  6a CANDIDATE GENERATION    ← Dijkstra's "expand neighbors"
       Generator: PERFORMER LLM with n=K candidates (sampled, not argmax)
       Optional: LIBRARIAN injects past-DAG moves at similar states
       Output: candidate set {c_1, …, c_K}

  6b PATH EVALUATION         ← Dijkstra's "compute f = g + h"
       Evaluator: ADVISOR (new role)
       g(c) = accumulated cost so far (tokens/wall/USD) — already in cost.* fields
       h(c) = estimated remaining cost (from retrieved past DAG outcomes)
       Output: ranked candidates with f-scores

  6c ELECTION                ← Dijkstra's "pop min f"
       Selector: deterministic argmin over scored candidates
       (Legal verb: the obligor ELECTS among means of performance)

Step 7 PERFORM-DISPATCH (still inside PERFORM step)
       Run the elected capability. No choice; pure execution.
```

### Implementation options

| | Option I (v1.7) | Option II (v1.8) |
|---|---|---|
| Trigger | LIBRARIAN injects retrieved moves into PERFORMER prompt as *hints* | Full split into 6a/6b/6c with explicit ADVISOR component |
| LLM calls per iteration | 1 (performer) + 1 (librarian retrieval; lookup-only, may not need LLM) | K (candidate generation) + 1 (advisor scoring) |
| Tracedata | one performance act per iteration | K candidates + scores + chosen, all in trace |
| When useful | as soon as DAG corpus has tens of past traces | when corpus is large enough that h() is meaningfully informed |
| Architectural change | low — just enrich the performer prompt | high — new sub-steps + new role |

**Decision: ship Option I in v1.7. Option II only if Option I proves
limiting (i.e., past-DAG retrieval signal exceeds what the PERFORMER LLM can
absorb as prompt hints).**

## 6. Risk + mitigation

- **Renaming risk: missed references break tests.**
  Mitigation: `git grep` exhaustively for each old token before/after; run full test suite (`pytest tests/ -q`) after every batch of renames.

- **Stale data files reference old event kinds.**
  Mitigation: `cat/trace.py` keeps the old `EventKind` literals AS WELL AS the new ones for backwards-read compatibility. Old `dag.json` files / trace JSONLs from before this PRD remain parseable. The `EVENT_TO_LAYER` map in `dag.py` accepts both old and new kinds.

- **Trace viewer breaks on old recordings.**
  Mitigation: `cat/dag.py` has an alias map: `contract_decompose` → treated as `contract_stipulate`. Reports of pre-rename runs still render.

- **Decision log drift.**
  Mitigation: this PRD becomes the canonical decision record. Future tasks reference it by ID (1.6.2.9).
