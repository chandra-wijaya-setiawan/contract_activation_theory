# v1.7 — Post-A.2 refinements (planned)

After A.2 ships and we measure on swe10, several refinements become
visible. This PRD captures the option space so we can decide based on
data, not speculation.

## Context

A.2 smoke result (2026-05-30, 3 tasks):
- 2/3 PASS (no regression)
- **Striking token savings: −53% on the two PASSes, −15% on the FAIL**
- 10 ELECTION events fired, **all deferred** (no overrides)

The savings happened but the math layer didn't directly cause them.
A.1 advisory hint + the new 2-candidate prompt + corpus growth (25 → 28
trajectories between runs) all contributed. We can't yet attribute.

## Refinement (1) — `librarian_hint` trace event [APPROVED, ship before swe10]

**Motivation.** Today the A.1 hint is transient — injected as a system
message that gets sent to the LLM but never recorded. We can't count
hint emissions or attribute behavior changes to them.

**Change.** When `_librarian_hint` produces a non-empty hint and that
hint is actually injected into the messages, emit a `librarian_hint`
trace event with:
- contract_id, iteration
- state_class (the leaf the librarian looked up)
- recommended tool + canonical_args + total_score
- confidence_n (how many observations the recommendation rests on)

Schema: add `"librarian_hint"` to `EventKind` literal in `cat/trace.py`.

**Effort.** ~15 lines. Pure observability, no behavioral change.

**Why ship before next swe10.** Without it we can't tell whether the
−53% comes from the hint (frequent + high-signal) or just the prompt
shift. Decision depends on which is the load-bearing channel.

## Refinement (2) — action canonicalization audit [data-dependent]

**Motivation.** Smoke showed elections firing with candidates like
`read /testbed/django/db/models/expressions.py offset=557 limit=100` —
but the corpus has `read /testbed/django/db/models/expressions.py`
(no offset). Different `action_class` → no match → defer.

The `canonical_action_args` function buckets `offset`/`limit` into
`small/medium/large`. The question: is the bucketing too narrow
(distinguishing reads that should be equivalent), too coarse
(merging reads that ARE different), or right but the corpus is just
small?

**Change.** A `scripts/audit_action_canonicalization.py` that:
1. Walks the corpus
2. Groups samples by `(state_class, tool)` then by canonical args
3. Reports: how many distinct action_classes exist per (state_class, tool)?
4. Examines a few examples by hand: do the "different" canonical_classes
   actually represent different intents?

**Effort.** ~1 hour, analysis-only.

**Trigger.** Run after the next swe10 lands. If ELECTION defer rate
stays at ~100% AND audit shows the LLM's candidates are systematically
in different action_classes than the corpus, this is the bottleneck.

## Refinement (3) — concrete-recommendation hint reframe [data-dependent]

**Motivation.** A.1's hint says "prior runs at this state suggest:
read(path=..., offset=medium)". The LLM has to interpret "medium" and
guess concrete args. If the LLM emits its own concrete choice that
happens to canonicalize differently, the corpus doesn't recognize it.

**Change.** Restructure the hint so it surfaces the BEST (state_class,
action_class) pair concretely. Optionally also mention the closest
match the LLM might be emitting and how it differs.

```
Today:    "prior runs at this state suggest: read(path=<repo>/file.py, offset=medium, limit=small) ..."
Reframe:  "to maximize corpus reuse, your next tool call should match
           action_class=ab12cd34 — example: read(path=<repo>/file.py, offset=10..50).
           Different (path, offset, limit) buckets will not match this class."
```

This is a precision move: tell the LLM the SHAPE that matches, not just
a sample.

**Effort.** ~30 lines in `Librarian.format_hint` + a description-of-bucketing
docstring in the PERFORMER prompt.

**Trigger.** Only if (2) audit shows the canonicalization is sane but
the LLM keeps emitting just outside the bucket boundaries.

## Refinement (4) — passive corpus growth [no work]

**Motivation.** Override rate of 0% may simply be a corpus-size issue.
With 28 trajectories total and CEGAR refinement creating 36 leaves, many
leaves have n=1. Per the simulator math (PRD v1.7.0): override probability
scales with the chance both candidates appear in the corpus, which scales
with samples per leaf.

**Change.** None. Every run adds samples via post-run writeback.
Override rate is a metric to *watch*, not engineer.

**Expected timeline.** Override rate should start rising once a state_class
has n ≥ 5 observations. With ~10 samples per swe10 run after refinement,
that means ~3 swe10 runs from now.

## Refinement (5) — defer/override ratio in reports [low priority]

**Motivation.** Tool-economy KPI today reports tool_calls and tool_waste.
It doesn't report ELECTION metrics.

**Change.** Add to `run_report.py`:
- `n_elections` per task
- `n_overrides` per task (`winner_index != 0`)
- `n_defers` per task
- Roll-up histogram in the HTML report

**Effort.** ~50 lines in `run_report.py`. Independent of LLM behavior.

**Trigger.** Ship when (1) lands; same area of code.

## Sequencing

```
NOW (before swe10 finishes is ideal, but the in-flight run won't have it):
  (1) librarian_hint trace event

AFTER swe10 lands + report generated:
  Decide based on metrics:
    - If hint fires lots but elections still defer → (2) audit canonicalization
    - If audit shows the LLM systematically misses by one bucket → (3) reframe
    - If override rate is rising naturally → wait (4)
  Either way:
    - (5) ELECTION metrics in run_report

LATER:
  v1.7.0.x two-tier feature refactor (formalize action_intent at Capability
  registration; queue per existing PRD)
```

## What this PRD is NOT

- Not a commitment to ship any of (2)/(3)/(5)
- Not a redesign of A.2 (A.2 ships clean per its own PRD)
- Not a substitute for waiting on data — explicitly defer (2)/(3) until
  swe10 evidence
