# v1.7 A.3 — Path-level Dijkstra + canonicalization refinement (NEXT)

## Why this PRD exists

After v1.7 A.2 shipped + revert + strip-fix, the LIBRARIAN fires every
turn (telemetry confirmed) but its hints are **single-edge** recommendations
with **confidence_n=1**, repeated every iteration, and ignored by the LLM
~80% of the time. The mechanism technically uses Dijkstra (backward-Dijkstra
computes d* offline), but at runtime we throw away most of Dijkstra's
output (the `parent[]` table that reconstructs the actual shortest PATH)
and serve only `argmin(cost(s,a) + d*(s'))` — one step.

This is a degenerate Dijkstra layer. The user's mental model — and the
intended design — was for the LIBRARIAN to recommend a **full path** to
the goal, not a single next move, and for the canonical state hashes to
make progress-equivalent points across different runs collide so the
corpus actually accumulates evidence.

This PRD fixes both.

## Research basis (same as v1.7.0)

- **Mechanism — TriCEGAR (CEGAR predicate tree)**. Raw features kept
  unhashed; abstraction is a function the tree applies. Starts maximally
  coarse; splits earn into the tree on counterexamples.
  *Source: TriCEGAR: A Trace-Driven Abstraction Mechanism for Agentic AI;*
  *Clarke et al. CAV 2000 (CEGAR original).*

- **Criterion — Ferns/Precup value bisimulation**. Two states belong
  in the same class iff their cost-to-GOAL distributions match. CV of
  realized cost-to-goal is the trigger; the tree splits the leaf with
  highest CV via a depth-1 decision stump.
  *Source: Ferns & Precup, Bisimulation Metrics are Optimal Value Functions, UAI 2014.*

- **Objective — Dijkstra**. Shortest-path on the corpus graph. We
  compute d* via backward Dijkstra from GOAL; the **parent table**
  (which we currently throw away) gives the actual path. This PRD
  surfaces it.

## Change 1 — Expose the full shortest PATH at runtime

### Today

```
Librarian.recommend(raw_features) → Optional[Recommendation]:
    one (action, expected_cost, d*(next)) tuple
```

### Proposed

```
Librarian.recommend_path(raw_features) → Optional[PathRecommendation]:
    Full path: list of (action, expected_next_state_class, cumulative_cost)
    Total expected cost to GOAL
    Minimum confidence_n across the path (the bottleneck observation count)
    Number of distinct prior trajectories that traverse this path
```

### Implementation

In `cat/librarian.py`:

1. **Backward Dijkstra now records `parent[]`** — for each state, the
   (action, next_state) edge that yielded its d* value. ~5 lines added
   to `_backward_dijkstra`.

2. **New method `Librarian.recommend_path(raw_features)`**:
   - Compute state_class
   - If state in graph AND d*(state) ≠ ∞:
     - Walk parent[] from current state to GOAL
     - Collect (action_klass, expected_state, cumulative_cost) at each hop
     - Return the path
   - Else: return None (cold state)

3. **Format hint** as multi-step path:
   ```
   Corpus path to goal (n=N prior PASS runs traversed this):
     1. rg pattern=settings_to_cmd_args_env  (expected ↓6 cost)
     2. read django/db/backends/postgresql/client.py  (expected ↓8K)
     3. str_replace postgresql/client.py            (expected ↓18K)
     4. bash 'python -m pytest --tb=short -q'        (expected → GOAL)
   Total expected: 32K tokens. Confidence: min n=2 across path.
   ```

4. **Keep the existing `recommend()` for backward compat** — it just
   returns the first edge of `recommend_path()`'s output, so any caller
   that wants a single-edge can still get one. ELECTION code stays
   unchanged.

### Acceptance for Change 1

- `Librarian.recommend_path()` returns a list of ≥1 hop on a non-empty
  corpus where the current state has a finite d*
- Hint text shows the multi-step path with confidence_n
- Existing `recommend()` keeps returning a single-edge `Recommendation`
- New unit test: seed corpus with 2-step PASS trajectory, recommend_path
  returns the 2-hop path with cumulative costs

## Change 2 — Canonicalization that makes progress-equivalent states collide

### The diagnostic from the smoke

In the django-11239 smoke after the strip fix:
- 52 hints fired (every iter)
- 51 of 52 used the SAME action_klass recommendation (rg pattern=...)
- BUT the LLM took 52 DIFFERENT paths through the workspace (read different
  client.py files in postgresql/, base/, mysql/ subdirs)

The corpus had ONE successful path; it recommends that path from every
state. The LLM diverges 80% of the time because the recommendation is
based on n=1 evidence. The corpus has no other "Pass paths" to
cross-reference because the canonicalization treats every (read different
file) as a different action, so prior PASS trajectories that read
DIFFERENT files don't accumulate evidence at the same state_class.

### The principle (Ferns/Precup)

Two states with **equivalent cost-to-GOAL** belong in the same class.
"I've read 3 client.py files and made 0 edits" should be the SAME state
regardless of WHICH 3 files — because the cost-to-finish-the-fix is
about the same.

We violate this today because `attempted_actions` is a set of
`action_class` hashes that include specific file paths in `canonical_args`.

### Proposed

Replace `attempted_actions` (in CORE_FEATURES) with `attempted_action_intents`:
a frozen multiset of `{investigate, mutate, verify, other}` counts.

```python
# OLD CORE feature
"attempted_actions": ["read-a-action-class", "rg-b-action-class", ...]

# NEW CORE feature
"attempted_action_intents": {"investigate": 3, "mutate": 0, "verify": 0}
```

The specific action_class hashes move to `domain_features.attempted_actions`
— they remain available for the CEGAR tree to split on IF the data
demands tighter refinement. By default, the BASE state collides across
"different files of equivalent intent."

### Why this is principled (not just looser hashing)

The CEGAR loop refines on counterexamples — high cost-to-goal variance.
If two trajectories that hash-to-same-state ACTUALLY have different cost
distributions, CEGAR detects it and SPLITS the leaf on a domain-specific
feature (e.g., the specific action_class). If they're truly equivalent,
no split fires; the merge holds.

So we start coarse (intent-only) and let the tree earn splits from data.
Today we start TOO FINE (specific file paths) and CEGAR can't merge
back; coarse-to-fine refinement is the natural direction.

### Implementation

In `cat/state_class.py`:

1. **`_FeatureState`** track:
   - `investigate_count`, `mutate_count`, `verify_count` already there
   - Drop the `attempted_actions` set from CORE keys; move into
     `domain_features` as a sparse list
   - Add `attempted_action_intents` to CORE keys: a 3-int tuple
     `(investigate_count, mutate_count, verify_count)` (we already count
     these — we just promote them to first-class)

2. **`CORE_FEATURES`** set updated:
   ```python
   CORE_FEATURES = {
       "obligation_hash", "plan_idx", "last_outcome", "last_action_intent",
       "durable_change_count", "iter_since_durable_change",
       "verify_attempt_count", "investigate_attempt_count", "mutate_attempt_count",
       "n_unique_errors",
       # REMOVED: "attempted_actions" (moves to domain_features)
       # REMOVED: "n_unique_actions" (subsumed by per-intent counts)
   }
   ```

3. **Migrate the corpus** — re-ingest every existing trace under the new
   canonicalization. The state_class hashes will change; the underlying
   trajectories are the same. A one-shot script: drop the `sample` table,
   re-walk every `trajectory` row's source JSONL.

### Acceptance for Change 2

- Two trajectories that read different files but reach equivalent
  progress points produce the SAME state_class at those points
- Verified by a focused test: 2 synthetic traces with different
  investigate paths but identical mutate steps; the post-investigate
  pre-mutate state_class hash matches
- CEGAR tree retains the ability to split on `domain_features.attempted_actions`
  IF cost variance demands; verified by a synthetic test with cost
  divergence
- The django-11239 corpus retains its existing PASS trajectories after
  migration

## Combined acceptance (run-time)

Run the existing django-11239 smoke with Change 1 + Change 2:
- librarian_hint events still fire (telemetry still works)
- recommend_path returns a MULTI-step path (not single edge)
- The hint shown to the PERFORMER includes the full predicted path
- A FAIL trajectory now consumes ≤ baseline tokens (no longer worse;
  ideally improves)
- A PASS trajectory's hint over multiple iterations shows the SAME
  path (consistency) rather than the same single edge

## Out of scope

- Forced N candidates in PERFORMER prompt — separate change, not
  blocked by this one
- LLM-judge chooser cascade — separate change
- Tree visualization — nice-to-have for debugging, defer

## Cost analysis

- Path-level recommendation: ~50-100 extra tokens per turn (vs current
  ~200 token hint). The path is presented inline; the LLM sees more
  but the surrounding hint scaffolding is unchanged.
- Canonicalization change: requires one-time corpus rebuild. After
  that, runtime cost is identical (same number of tree-walk + dict
  lookups).
- Total runtime overhead: negligible. The Dijkstra is still
  precomputed offline.

   full swe10.

## What this PRD does NOT promise

- That solve rate will go up. We don't yet know how much of the
  django-11239 regression was LLM variance vs hint noise vs other.
- That ELECTION will start overriding. Without forced N≥2 candidates,
  ELECTION still rarely fires.
- That the corpus is "right-sized." It's still 50 trajectories. The
  hints will be more useful but still under-supported.

What it DOES promise: the Dijkstra layer will be REAL — full-path output,
canonical state hashes that collide across different paths reaching the
same progress point. The mechanism stops being lookup-and-pray.
