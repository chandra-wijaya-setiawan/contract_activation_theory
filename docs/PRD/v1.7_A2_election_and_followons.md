# v1.7 Phase A.2 — ELECTION + follow-ons (NEXT)

> Single PRD for the v1.7 learning-loop completion: math arbitrates
> actions today (A.2); optional improvements (A* heuristic) and lifecycle
> tweak (SUSPENDED resume) ship behind it only if data demands.

## Primary: A.2 — ADVISOR + ELECTION (the experiment)

### Goal

Make the math actually control behavior. Today (A.1) the LIBRARIAN returns
a Dijkstra recommendation as a text hint; the LLM may or may not heed it.
A.2 introduces multi-candidate generation + math-arbitrated selection.

### Concrete change

1. **Performer prompt update** — ask LLM to emit **N=2** candidate tool
   calls per turn (or split into two turns: emit one, get hint, emit
   alternative).

2. **`Librarian.score_candidates(candidates, raw_features) → ScoredList`**
   for each candidate action, compute
   `score(a) = expected_cost(a) + d*(next_state | s, a)`.
   Unknown `(s, a)` pairs fall back to a global prior with `defer=True`.

3. **ELECTION step in `Activator._perform_once`** — execute the
   lowest-scored candidate. If all candidates DEFER (no corpus signal),
   execute the first one (LLM's preferred choice — preserves backward-
   compat on cold states).

4. **`election` trace event** — records winner + losers + scores so we
   can audit "would have picked X, elected Y" cases.

5. **Synthetic test** — case where corpus has a clearly cheaper path;
   verify ELECTION picks it over the LLM's default.

### Validation

Rerun the 3-task smoke with A.2 enabled. Compare:

- Same 2/3 PASS rate (no regression)
- Tool counts and per-task tokens vs A.1 advisory
- Trace `election` events: how often does math override the LLM, and on
  what kinds of actions?

### Estimated work

~150 LOC across `activator.py` + `librarian.py` + a small
`PERFORMER_SYSTEM_PROMPT` change. ~1 hour focused.

## Follow-on 1: A* heuristic h(v) — only if A.2 underperforms

### When to ship

A.2 above uses `score(a) = expected_cost(a) + d*(next_state)`. This is
strict Dijkstra over observed edge weights. If A.2's solve rate matches
v1.7-tools or better, ship is sufficient. Only add A* if:

- Cold-state DEFER rate is so high that the corpus rarely fires
- d* values converge slowly on small corpora (variance still high after
  CEGAR refinement)

### Change

Replace `d*(next)` in the score formula with:

```
h(s) = 25th-percentile cost-to-goal observed in PASS trajectories
       passing through s's state_class
```

25th percentile keeps the heuristic *admissible* (never overestimates)
which preserves A* optimality guarantees.

### Estimated work

~30 LOC. One helper function + 5-line change in the score formula.

## Follow-on 2: SUSPENDED resume (DAG-grounded) — only if observed

### When to ship

Don't preemptively. Wait until post-A.2 traces show suspend-cases that
would actually benefit. Two signals worth watching:

- High self-loop fractions in state classes (the f59669ec pattern from
  v1.7.0 walkthrough)
- Contracts terminating via budget violation despite the corpus having
  cheaper paths from earlier states

### Change

When contract enters SUSPENDED:

1. Walk DAG back to the last `neutral`-tagged ancestor
2. Prune the dead-end subtree below it from the active conversation
3. Re-enter ACTIVE from that point with a fresh performer turn

The mechanic uses the outcome tags from the corpus, not the live trace.

### Estimated work

~80 LOC in activator + lifecycle.

---

## Sequence

1. Ship A.2 alone first. Measure on swe10 (smoke + full).
2. If A.2 outcome is good: stop here. Phase A is done.
3. If A.2 has visible weakness in the cold-state / fast-corpus path: add
   the A* heuristic.
4. If post-A.2 traces show stuck-state patterns at scale: add SUSPENDED
   resume.
5. Otherwise both follow-ons stay backlog. Move on to v1.7.1 SkillsBench.

The principle: **ship the experiment, then ship fixes for problems we
actually see** — not problems we imagine.
