# v1.4 — SkillsBench cross-domain validation (FUTURE)

Replaces the prior v1.4 tau-bench plan. See site
[skillsbench.ai/leaderboard](https://www.skillsbench.ai/leaderboard) and
repo [benchflow-ai/skillsbench](https://github.com/benchflow-ai/skillsbench).

## Goal

First non-code-only benchmark for CAT. Validate that the framework's
discipline + the v1.7 learning loop generalize beyond SWE-bench.

## Why this benchmark (vs tau-bench, vs others)

- **11 professional domains** in 92-94 tasks. Cross-domain generalization
  test built in, no separate per-domain integration.
- **Outcome-based deterministic verifier** per task. Matches CAT's
  oracle preference; no LLM-judge work.
- **Docker per task** (same harness shape as SWE-bench). Adapter is
  mostly mechanical port of `benchmarks/swe_bench.py`.
- **Reference oracle solutions** per task — lets us audit "what should
  have happened" cheaply.
- **Established scaffolds already on the leaderboard** — Claude Code,
  OpenHands, Gemini CLI, Codex, plus the frontier proprietary models.
  Head-to-head numbers are public.
- **Folds in part of v1.8 hardening** (head-to-head vs established
  agents) since the leaderboard already has the comparisons we'd want.

## Engineering work

1. **`benchmarks/skillsbench.py`** — adapter wrapping the BenchFlow CLI:
   - Install: `uv tool install benchflow`
   - Per-task: `benchflow run tasks/<task-id> --agent cat-tb --model <model>`
   - `TbCatAgent` already implements `terminal_bench.agents.base_agent.BaseAgent`;
     check whether SkillsBench's harness accepts the same interface OR
     uses BenchFlow's own. If different: thin shim.

2. **Task representation** — 92-94 tasks across 11 domains; each has a
   task instruction (markdown), a Dockerfile, an oracle solution, and an
   outcome verifier. The verifier runs after the agent stops; exit code
   determines PASS/FAIL.

3. **Capability registry per domain** — the docker registry from v1.6.6
   covers code domains; other domains may need different default tools
   (browser? data-analysis? config-editing?). The v1.7.0.x two-tier
   refactor matters here: `action_intent` should classify whatever tools
   each domain registers.

4. **Corpus seeding** — bootstrap the LIBRARIAN corpus with oracle
   trajectories per task (the reference solutions). Gives Phase A.2
   ELECTION something to recommend against from day one, rather than
   cold-start on every domain.

5. **Run configuration** — full 94-task benchmark; 3 trials per task
   (matches the leaderboard convention). ~3-4 hours wall time at
   concurrency 10.

## Validation targets

- **Solve rate** on the full 94 tasks. Compare to leaderboard:
  - Beat Codex / OpenHands / Gemini CLI: a real win
  - Within the band of Claude Code: parity is acceptable on first run
  - Below Codex: investigation needed (likely the cross-domain feature
    gap surfaces here)
- **Per-domain breakdown** — which of the 11 domains CAT handles well
  vs poorly. Drives prioritization for v2.x cross-domain work.
- **Tool-call efficiency** vs Claude Code (the relevant frontier
  scaffold) — we've measured -55% on SWE-bench; does that hold on
  non-code domains?
- **Cross-domain transfer in the corpus** — does the LIBRARIAN's
  predicate tree pick CORE features more often than DOMAIN features
  when the corpus contains traces from 11 domains? (Hypothesis from
  PRD `v2x_cross_domain_features.md`: yes — domain-agnostic predicates
  like `verify_attempt_count > 3` should dominate the tree.)

## What this also delivers

- **Folds in v1.8 head-to-head** for the established scaffolds we
  care about (Claude Code, OpenHands). v1.8 becomes specifically about
  agent-framework comparison (Pi, Hermes) which the leaderboard doesn't
  cover.
- **Empirical pressure on the two-tier refactor** (v1.7.0.x). One
  domain = no pressure to refactor; 11 domains = the refactor pays
  off immediately or doesn't.
- **Real signal for v2.x deferred items** — procedural memory,
  cost-eff layer, capability granting — multi-domain corpus is the
  setting where their value is testable.

## Open questions before starting

1. **Agent interface compatibility.** Does SkillsBench's `benchflow run
   --agent <name>` accept our `cat-tb` BaseAgent, or do we need a
   different entrypoint? Check `benchflow-ai/benchflow` SDK.

2. **Trajectory format compatibility.** SkillsBench publishes trajectories
   via HuggingFace `benchflow` org. Do we want to publish ours alongside
   (transparency), or keep them private until we're confident?

3. **Excluded tasks.** 9 tasks require external API keys (OpenAI, GitHub,
   HuggingFace, Modal). Run without them first; revisit if those 9 are
   load-bearing for our claims.

4. **Reasoning effort setting.** Leaderboard uses "highest available
   reasoning effort." We're on `deepseek-v4-flash` (fast tier). The
   token-efficiency comparison should be at matched-effort, not
   matched-model. Decide whether to upgrade for the validation run.
